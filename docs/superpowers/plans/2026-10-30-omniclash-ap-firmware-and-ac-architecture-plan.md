## 一、 项目背景与终极愿景

在第二阶段中，OmniClash 实现了基于原生 HTTP 的结构化 `omniclash-agent` 与看门狗自愈回滚机制，将子 AP 通信延迟压缩至 0.4 秒。但在实际硬件工程落地中，使用通用原厂固件或普通第三方 OpenWrt 部署子 AP 仍存在几大体验痛点：

1. **初始网段冲突与双 DHCP 灾难**：全新开箱的 OpenWrt 硬路由器默认处于主网关模式（自带 `192.168.1.1` 与开启的 DHCP 服务器），接入已有局域网极易引发全网 IP 错乱与管理断连；
2. **多步配置门槛高**：用户需要手动上传 Agent IPK、手动停用自身 DHCP、手动提取 Token、手动配对，流程繁杂；
3. **闭源商用系统（如集客 AP）的局限**：集客等商业 AP 方案属于闭源黑盒，新 Wi-Fi 芯片适配滞后，且无法与 Mihomo 的 32 槽位 802.1Q VLAN 物理防泄漏流水线实现深层硬件联动。

### 终极愿景
打造开源专属的 **`OmniClash-AP OS`（定制 AP 固件）** 与 **`OmniClash-AC`（主控套件）**，实现类似 Ubiquiti UniFi 与集客的**“开箱盲插、零感纳管、断网自愈、双工通用”**的企业级商用网络体验。

## 二、 定制 AP 固件规格设计 (OmniClash-AP OS)

基于官方/ImmortalWrt **ImageBuilder（镜像构建器）**，采用积木式裁剪组装技术，在 2 分钟内压出各机型专属的极简瘦 AP 固件。

### 1. 硬件支持矩阵（首批主力）

| 机型名称 | 芯片平台 | 闪存/内存 | 核心特性 |
| :--- | :--- | :--- | :--- |
| **京东云鲁班 (RE-CP-02)** | MediaTek MT7981B (Filogic 820) | 128MB / 512MB | 5G 160MHz Wi-Fi 6，当前测试主力 |
| **红米 AX6000 (Redmi AX6000)** | MediaTek MT7986A (Filogic 830) | 128MB / 512MB | 高性能 4x4 MIMO Wi-Fi 6，旗舰带机 |
| **小米 AX3000T** | MediaTek MT7981B (Filogic 820) | 128MB / 256MB | 高性价比平民百元级 Wi-Fi 6 AP |

### 2. 极致瘦身与性能裁切 (Slimming & Footprint)

定制 AP 固件出厂即定位为纯物理层/二层透传无线发射台，移除一切不必要的网关负担：

* **彻底剥离的服务**：
  - ❌ `dnsmasq`（彻底杜绝自身发射 DHCP 引发主网瘫痪）；
  - ❌ `firewall4` / `nftables`（移除一切内网包过滤与连接跟踪开销，跑满千兆线速）；
  - ❌ `odhcpd` / `ppp` / `pppoe`（不承担任何拨号和 IPv6 路由分发）；
  - ❌ `luci` 臃肿页面（可选：制作极简 Headless 纯无头固件，或仅留 1 页状态展示板）。
* **内置核心组件**：
  - ✅ Linux 官方原生驱动栈：`mac80211` + `mt76` 芯片驱动；
  - ✅ 轻量运行环境：`ucode`、`ucode-mod-fs`、`ucode-mod-uci`、`ucode-mod-ubus`；
  - ✅ 原生轻量服务：`uhttpd`（提供 `/cgi-bin/omniclash-agent` 端点）；
  - ✅ 系统工具：`iwinfo`、`iw`、`ip-full`；
  - ✅ **出厂固化 `omniclash-agent` 最新生产版**。
* **物理指标预期**：
  - **固件体积**：压缩后 `< 16MB`；
  - **常驻内存消耗**：`< 35MB`（512MB 内存机器空闲度高达 90%+，杜绝内存泄漏崩机）；
  - **开机启动速度**：通电至无线完全发射 **`< 8 秒`**。

## 三、 网络双工自适应与全场景容灾设计

固件必须具备跨网络环境的高适应性，绝不与特定主路由强行绑死。

```text
                           ┌───────────────────────────┐
                           │   OmniClash-AP 开机启动   │
                           └─────────────┬─────────────┘
                                         │
                                   [ 网线盲插 ]
                                         │
                        ┌────────────────┴────────────────┐
                        ▼                                 ▼
             【检测到上级主路由】                      【无上级 / 未插网线】
                        │                                 │
            从主路由获取动态 IP                           超时触发本地自愈
            (192.168.100.x / 1.x)                         激活备用静态 IP:
                        │                                 192.168.100.2
                        │                                 发射救援 Wi-Fi:
           ┌────────────┴────────────┐                    OmniClash-Setup
           ▼                         ▼                            │
[上级为 OmniClash AC]       [上级为普通家用主路由]                │
           │                         │                            │
 自动开启 UDP 信标宣告      自动以标准双频 AP 运行                │
 激活 32-VLAN 物理隔离       (2.4G/5G 纯透明桥接)                 │
 专线防泄漏分流接入          千兆高速免配置上网                   │
           │                         │                            │
           ▼                         ▼                            ▼
    【企业级全托管】            【高性能无线扩展】            【永久可维护防砖】
```

### 1. 场景 A：连接 OmniClash AC 主控（主模式）
- **自动握手**：AP 通过主路由分配的 IP 与主控建立结构化通信；
- **全量物理隔离**：主控下推 32 槽位无线矩阵，AP 自动映射 `vlan101` ~ `vlan132` 桥接，数据帧打上 802.1Q 标签送入主路由 Mihomo 进行专线/分流物理锁死。

### 2. 场景 B：连接普通第三方主路由（通用扩展模式）
- **免任何设置**：随手插在华为、TP-Link、华硕或光猫的 LAN 口上；
- **全网口盲插**：WAN + LAN 统一桥接在单一 `br-lan`，全端口千兆交换；
- **零冲突、无感知**：AP 自动成为透明 Wi-Fi 6 信号放大发射器，客户端直接穿透从上级光猫/TP-Link 拿 IP，不经过双重 NAT，无任何兼容性问题。

### 3. 场景 C：没插网线 / 离线单机维护（容灾救援模式）
- **动态回退固定 IP (Fallback IP)**：
  若开机 15 秒内未获取到任何 DHCP 租约，底层后台自动唤醒 `192.168.100.2/24` 作为备用管理地址，电脑插网线设定静态 IP 即可瞬间直连；
- **出厂救援配网 Wi-Fi (Rescue AP)**：
  离线状态下自动保持一个默认热点 `OmniClash-AP-Rescue`（密码：`12345678`），手机连入后可直接进入极简状态页查看物理射频健康度。

## 四、 控制通信与零感纳管协议 (Zero-Touch Adoption)

彻底替代传统手动输入 IP 与 Token 的配对模式。

### 1. 局域网广播信标协议 (AP Beacon)
AP 通电获取 IP 后，后台常驻线程以 `10 秒` 为周期向局域网广播地址发送 UDP 信标报文：
- **目标**：`255.255.255.255:7899`
- **报文格式** (JSON)：
  ```json
  {
    "magic": "OMNICLASH_BEACON",
    "version": "0.1.0",
    "mac": "dc:d8:7c:41:d4:fd",
    "ip": "192.168.100.15",
    "hostname": "OmniClash-AP-LuBan",
    "model": "jdcloud,re-cp-02",
    "status": "unadopted"
  }
  ```

### 2. AC 主控零感领养流程 (One-Click Adoption)
1. **自动监听**：主路由 OmniClash 后台常驻监听 `UDP 7899` 端口；
2. **气泡提醒**：收到未纳管信标时，LuCI 前端弹窗提示：
   > 🔔 **发现待接入的子 AP 硬件**：`OmniClash-AP-LuBan (192.168.100.15)`
3. **一键纳管**：点击【一键纳管】，主控生成随机安全 Token 并经由一次性握手推送给 AP，AP 固化 Token 并关闭信标广播，主控自动开始推送 32-WiFi 矩阵配置。

## 五、 自动化固件构建工厂 (CI/CD Pipeline)

无需在本地搭建数十 GB 的交叉编译环境，借助 GitHub Actions 实现云端持续集成出包。

```text
本地 Git 仓库                    GitHub Actions 云端 Runner
      │                                       │
      ├─────── git push tag (v*) ────────────►│
      │                                       ├─ 下载官方 ImageBuilder 归档
      │                                       ├─ 注入 omniclash-agent 预编译包
      │                                       ├─ 注入专属出厂 uci-defaults 配置
      │                                       ├─ 执行 make image 生成固件
      │                                       ├─ 计算 sha256 校验和
      │                                       │
      │◄────── 发布至 Releases 页面 ───────────┴─ 产出 omniclash-ap-luban.bin
```

### 核心构建配方示例
```bash
make image \
    PROFILE="jdcloud_re-cp-02" \
    PACKAGES="-dnsmasq -firewall4 -nftables -ppp -odhcpd -luci \
              ucode ucode-mod-fs ucode-mod-uci ucode-mod-ubus \
              uhttpd iwinfo iw ip-full kmod-mt7981-firmware" \
    FILES="custom_root/"
```

## 七、 总结

本方案在保持主路由 Mihomo 核心与 32 槽位 VLAN 物理防泄漏绝对优势的前提下，将子 AP 的使用门槛彻底抹平为**“刷入固件，插线即用”**。既具备商用 AP 的傻瓜化便捷，又完全享有原生 Linux 开源驱动的高性能与透明度。
