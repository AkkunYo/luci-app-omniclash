# OmniClash 分流配置全景可视化与应用卡片流系统设计

## 1. 背景与业务痛点

在 OmniClash 现行架构中，分流配置与规则管理虽然在 UI 上拆分为了“Provider 订阅集”、“分流节点组”和“分流规则”若干子页面，但仍存在以下本质缺陷：
1. **暗箱组装**：六层规则流水线大量逻辑硬编码于底层执行脚本中，前端无法直观感知或自由编排整条流水线的上下层级关系；
2. **规则与策略组割裂**：传统以纯规则类型（`GEOSITE`, `DOMAIN-SUFFIX` 等）为核心的平铺表格难以直观反映真实业务场景，用户调整一个应用的出口走向往往需要在规则表和策略组之间反复来回切换；
3. **缺少实时闭环**：修改策略组过滤或规则走向后，无法即时确认命中关系，缺乏“所见即所得”的确定感。

本设计旨在将原本晦涩的底层规则流重构为**“应用驱动卡片流 (Application-Driven Card Stream)”**，同时保证专线 WiFi 物理拦截高于一切，杜绝规则截胡与 IP 泄漏。

## 2. 总体架构与数据模型

### 2.1 存储模型设计 (`/etc/omniclash/apps.json`)

系统废弃旧版扁平的 `rules.json`，改用结构化、支持用户精细扩展的 `apps.json`：

```json
[
  {
    "id": "ai",
    "name": "🤖 AI 场景服务",
    "desc": "ChatGPT / Claude / OpenAI / Anthropic 等主流大模型与 AI 接口",
    "target": "🎯 专线-Tallflix",
    "builtin_rules": [
      { "type": "GEOSITE", "payload": "category-ai-chat-!cn" },
      { "type": "GEOSITE", "payload": "openai" },
      { "type": "GEOSITE", "payload": "anthropic" }
    ],
    "custom_rules": [
      { "type": "DOMAIN-SUFFIX", "payload": "oaistatic.com" }
    ],
    "enabled": true,
    "is_custom": false
  },
  {
    "id": "youtube",
    "name": "📹 YouTube 媒体",
    "desc": "YouTube 视频、音频及分发 CDN 流量",
    "target": "🇭🇰 香港节点",
    "builtin_rules": [
      { "type": "GEOSITE", "payload": "youtube" }
    ],
    "custom_rules": [],
    "enabled": true,
    "is_custom": false
  }
]
```

#### 字段规范说明：
* `id`: 全局唯一标识，自定义应用采用 `custom_` 前缀；
* `name`: 显示于卡片顶部的业务名称与图标；
* `desc`: 业务场景功能简述；
* `target`: 该应用卡片绑定的出口走向（来自策略组全景或系统直连/拦截）；
* `builtin_rules`: 系统标准化预设规则库，恢复默认时重置；
* `custom_rules`: 用户针对该场景自主追加的私有域名或 IP 匹配项；
* `enabled`: 布尔值，控制该应用卡片是否参与底层规则编译；
* `is_custom`: 标识是否为用户自主新建的业务卡片。

### 2.2 基础模板保护 (`/etc/omniclash/apps_default.json`)
源码仓库常驻标准脱敏全套应用模板，支持一键无损重置：
* 预置场景包含：`🤖 AI 场景服务`、`📹 YouTube 媒体`、`🎥 NETFLIX 流媒体`、`📲 Telegram 通讯`、`🍀 Google 服务`、`🐙 GitHub 开发者`、`📹 哔哩哔哩海外`、`🎵 Spotify`、`📹 巴哈姆特`、`🐬 OneDrive`、`🪟 Microsoft`、`🎵 TikTok`、`📖 Notion`、`💶 PayPal`、`🐦 Twitter / X`、`🍎 Apple 服务` 等 16 大主流场景。

## 3. 铁律流水线：物理专线最高优先级防截胡机制 (Ironclad Pipeline)

在合流编译时，严格遵循**“物理来源优先于应用内容 (Source > Content)”**原则，确保专线物理隔离绝对安全：

```text
┌────────────────────────────────────────────────────────────────────────┐
│                        Mihomo 真实数据包匹配流水线                     │
└────────────────────────────────────────────────────────────────────────┘
                                    │
                                    ▼
┌────────────────────────────────────────────────────────────────────────┐
│ 🥇 Layer 1: 私网直连与防劫持 (192.168.x / 10.x 直连，内网互通基石)      │
└───────────────────────────────────┬────────────────────────────────────┘
                                    │ 未命中
                                    ▼
┌────────────────────────────────────────────────────────────────────────┐
│ 👑 Layer 2: 【全局专线 WiFi (01~08)】绝对拦截区 (专线锁死，防泄漏第一线)│
│    - 数据包来源匹配: SRC-IP-CIDR 192.168.101.0/24 ~ 108.0/24           │
│    👉 无论访问 YouTube、Google 还是其它网站，最顶层直接送往专线出口！  │
│    👉 数据包在此层瞬间完成路由，绝对不会流经后续的任何应用规则！       │
└───────────────────────────────────┬────────────────────────────────────┘
                                    │ 未命中 (非全局 WiFi 设备)
                                    ▼
┌────────────────────────────────────────────────────────────────────────┐
│ 🥈 Layer 3: 【定向分流 WiFi (09~16)】绝对拦截区                        │
│    - 国内 IP / 域名: 强制直连 (秒开)                                   │
│    - 国外所有流量: 直接强制送往专属专线出口，同样绝不被后续应用截胡！    │
└───────────────────────────────────┬────────────────────────────────────┘
                                    │ 未命中 (仅通用分流 WiFi 与主网络设备)
                                    ▼
┌────────────────────────────────────────────────────────────────────────┐
│ 🥉 Layer 4: 广告拦截区 (仅通用分流设备生效，绝不误杀工作机)            │
└───────────────────────────────────┬────────────────────────────────────┘
                                    │ 未命中
                                    ▼
┌────────────────────────────────────────────────────────────────────────┐
│ 🎯 Layer 5: 【业务应用卡片流】(仅对通用分流 WiFi / 主网络设备生效)     │
│    - 按卡片在 UI 上的先后顺序发射规则：                                │
│      展开卡片内置 rules 与 custom_rules，统一定向至卡片选定的 target 组 │
└───────────────────────────────────┬────────────────────────────────────┘
                                    │ 未命中
                                    ▼
┌────────────────────────────────────────────────────────────────────────┐
│ ⚓ Layer 6: 通用分流 WiFi (17~32) 专属出口兜底                          │
│ ⚓ Layer 7: MATCH 最终漏网兜底                                          │
└────────────────────────────────────────────────────────────────────────┘
```

## 4. 前端交互与视觉布局规范

### 4.1 页面层次划分
在【订阅与分流】页面的【🔀 业务应用分流全景】子 Tab 中分为三层：
1. **🛡️ 硬件隔离专线通道保障栏（置顶提示区）**：
   * 柔和绿色提示条，明确告知用户：全局专线模式与定向模式享有硬件级最高匹配优先级，专线设备绝不走下方的 YouTube/Google 分流。
2. **🚀 业务应用分流流水线（核心操作区）**：
   * 右上角提供操作栏：【`+ 新建场景卡片`】与【`🔄 恢复默认应用库`】；
   * 每张应用卡片采用紧凑 Flex 结构：
     * **常规收起状态**：图标 + 名称 + 规则数量徽标 + 核心走向下拉选择框 + 上移/下移/展开/删除按钮；
     * **展开状态**：内嵌展示预置规则只读列表，以及用户自定义规则微表格（支持快速输入域名与 IP 段，即时添加）；
   * 点击 `↑` / `↓` 按钮即时调换卡片上下次序，对应在底层合成时的匹配先后顺序。
3. **⚓ 基础保障与兜底收口区（系统锁定）**：
   * `私网直连与防劫持`：锁定最前；
   * `🇨🇳 国内直连 (CN)` 与 `🐟 漏网之鱼 (MATCH)`：锁定最后。

### 4.2 保存机制
所有前端改动（调整出口下拉框、微调卡片顺序、追加自定义域名）统一依托 OpenWrt 官方原生的 `form.Map` / `uci.changes`，点击页面右下角官方底栏【保存并应用】，系统原子调用 RPC 完成配置合流并热重载。

## 5. 后端编译与热重载保障 (`/usr/bin/omniclash`)

### 5.1 编译流程
1. 读取 `/etc/omniclash/apps.json`；
2. 提取当前所有启用卡片，按卡片顺序解包其包含的 `builtin_rules` 与 `custom_rules`；
3. 将规则以 `TYPE,PAYLOAD,TARGET` 格式拼装进完整六层流水线的 Layer 5；
4. 输出至临时文件 `/tmp/omniclash_compiled.yaml`；
5. 调用 `mihomo -t -d /etc/omniclash/run -f /tmp/omniclash_compiled.yaml` 执行语法沙箱校验；
6. 校验通过执行原子覆盖：`mv -f /tmp/omniclash_compiled.yaml /etc/omniclash/run/config.yaml`；
7. 校验失败丢弃临时文件，阻止断网。

### 5.2 毫秒级热重载
调用 Mihomo 核心接口 `PUT http://127.0.0.1:9090/configs`，长连接无感切换。

## 6. RPC 服务端接口规范 (`luci.omniclash`)

* `get_apps`:
  * 无参，读取并返回 `apps.json` 完整数据；
* `save_apps`:
  * 参数：`apps: []`；
  * 保存更新至 `apps.json`，并触发原子编译与平滑热重载；
* `reset_apps`:
  * 无参，从 `apps_default.json` 恢复全量默认应用库，并触发原子编译与平滑热重载。
